## 문제 요약

음이 아닌 정수 배열 `numbers` 의 **순서를 바꾸지 않고** 각 원소 앞에 `+` 또는 `-` 를 붙여
합이 `target` 이 되는 **방법의 개수**를 구한다.

- `numbers` 길이: **2 ~ 20**
- 각 원소: **1 ~ 50** 인 자연수 → 전체 합 최대 **1,000**
- `target`: **1 ~ 1,000**
- 예: `[1,1,1,1,1]`, `target=3` → 5가지 / `[4,1,2,1]`, `target=4` → 2가지

## 풀이 접근

부호를 `+`/`-` 두 갈래로 나누는 대신, **전부 `+` 인 상태에서 시작해 부호를 뒤집을 때마다
`2 * num` 을 빼는** 방식으로 [DFS](../../../concepts/algorithm/dfs-bfs.md) 를 돌렸다.

1. `solution` 에서 전체 합을 먼저 구하고, `target` 을 필드에 저장한 뒤 `dfs(합, 0, 0)` 을 호출한다.
2. `dfs` 는 인덱스 `idx` 마다 두 갈래로 재귀한다 —
   `cur` 을 그대로 두는 분기(`+` 유지)와, `cur - nums[idx]*2` 로 내리는 분기(`-` 로 전환).
3. 방문 처리는 `visited` 를 **[비트마스크](../../../concepts/algorithm/backtracking.md) `int`** 로 두고 매 호출마다 `1 << idx` 를 켠다.
4. `visited` 가 `(1 << nums.length) - 1` 로 가득 차면 원소를 전부 썼다는 뜻이므로,
   `cur == t` 인 경우에만 `answer++` 하고 되돌아간다.
5. `solve` 진입 시 `answer = 0` 으로 초기화한다.

## 복잡도

`N = numbers.length` (문제 제약 2 ≤ N ≤ 20), `S = 전체 합 ≤ 1,000`

|---|---|---|
| Java | **O(2ᴺ)** — N=20 일 때 리프 1,048,576개 / 재귀 호출 **2,097,151회**, 실측 **4.9ms** | O(N) 재귀 스택 |
| C++ | **미구현** (템플릿 그대로) | — |

**통과 판정: 여유롭게 통과.** `2²⁰ ≈ 100만` 은 Java 에서 5ms 수준이다.
N 이 30만 돼도 10억이라 터지지만, 이 문제는 20에서 끊어준다.

> 예제 2개 + 무작위 300건을 DP 해와 교차 검증해 **불일치 0건**을 확인했다.

## 피드백

### 현재 풀이의 문제점

**1. `visited` [비트마스크](../../../concepts/algorithm/backtracking.md)가 아무 일도 하지 않는다 — 파라미터 하나가 통째로 군더더기**

```java
private void dfs(int cur, int idx, int visited){
    if(visited == (1 << (nums.length)) -1) { ... }
    dfs(cur, idx + 1, visited | (1 << idx));
    dfs(cur - (nums[idx]*2), idx + 1, visited | (1 << idx));
}
```

`dfs` 는 **항상 `idx` 번째 비트를 켜고 `idx + 1` 로 내려간다.** 둘이 완전히 맞물려 움직이므로
`idx` 단계에서 `visited` 는 **예외 없이** `(1 << idx) - 1` 이다. 즉 종료 조건

```java
visited == (1 << nums.length) - 1     ⟺     idx == nums.length
```

가 **항상 같은 뜻**이다. 비트마스크가 필요한 건 순열처럼 **어떤 원소를 이미 썼는지 순서와 무관하게**
기억해야 할 때인데, 이 문제는 `idx` 를 0부터 차례로 훑기만 한다.

지난 42839(소수 찾기)에서 비트마스크를 쓴 건 **옳았다** — 거기선 조각을 임의 순서로 골랐다.
여기서는 그 습관이 그대로 넘어왔지만 문제 구조가 다르다.

실측으로도 호출 수가 **2,097,151회로 완전히 동일**하다. 성능이 아니라 읽는 사람이 손해다.

**2. ~~static 필드 3개에 상태를 얹었다~~ — 해소됨**

`class Solution` 인스턴스 메서드로 바꾸면서 `nums`, `target`, `answer` 가 인스턴스 필드가 됐다.
채점기가 케이스마다 `new Solution()` 을 만들므로 초기화를 잊어 틀릴 일이 없다.

**3. ~~`t` 는 이름이 아니다~~ — 해소됨**

`target` 으로 바뀌었다.

**4. `cur` 이 "현재 합"인지 "남은 차이"인지 이름만으로 안 보인다**

전체 합에서 출발해 깎아 내려가는 값이다. `sum` 이나 `running` 쪽이 의도에 가깝다.

**5. ~~`import java.io.*` 와 `throws IOException` 이 안 쓰인다~~ — 해소됨**

제출본에서 `main` 이 빠지면서 같이 사라졌다.

### 다른 대안

**A. 비트마스크 제거 (권장) — 1·3·4번 동시 해결**

```java
private void dfs(int sum, int idx) {
    if (idx == nums.length) { if (sum == target) answer++; return; }
    dfs(sum, idx + 1);                  // + 유지
    dfs(sum - nums[idx] * 2, idx + 1);  // - 로 전환
}
```

호출 수·결과 모두 현재와 동일하다(2,097,151회 / 4.6ms). **파라미터 하나와 비트 연산이 사라질 뿐**인데,
`idx == nums.length` 가 "원소를 다 썼다"는 뜻을 훨씬 직접적으로 말한다.

**B. [DP](../../../concepts/algorithm/dp.md) — 부분집합 합으로 환원 (이 문제의 정석)**

`-` 를 붙일 원소들의 합을 `s` 라 하면 `(전체합 - s) - s = target`, 즉 **`s = (전체합 - target) / 2`** 다.
문제가 "합이 `s` 인 부분집합의 개수"로 바뀐다.

```java
public int solution(int[] numbers, int target) {
    int sum = 0;
    for (int n : numbers) sum += n;
    if (target > sum || ((sum - target) & 1) == 1) return 0;   // 도달 불가 / 패리티 불일치
    int s = (sum - target) / 2;
    int[] dp = new int[s + 1];
    dp[0] = 1;
    for (int n : numbers)
        for (int v = s; v >= n; v--) dp[v] += dp[v - n];       // 역순이라 각 원소 1회만 사용
    return dp[s];
}
```

| | 시간 | N=20 실측 |
|---|---|---|
| DFS (현재) | O(2ᴺ) = 100만 | 4.9ms |
| DP (대안 B) | O(N·S) = 20 × 1000 = **2만** | **0.007ms** |

**700배 빠르지만, 이 문제에서는 DFS 로도 충분하다.** DP 를 권하는 이유는 속도가 아니라
**N 이 40으로 늘면 DFS 가 즉사하는데 DP 는 그대로 돈다**는 점이다. 같은 문제가 백준·SWEA 에서
N 을 키워 나올 때 이 환원(부호 결정 → 부분집합 합)을 기억하고 있는지가 갈린다.

> 삼성 대비 관점에서는 **A 로 제출하고 B 를 손으로 한 번 쳐 보는 것**을 권한다.
> 커리큘럼 Phase 0 의 목표는 "DFS 뼈대를 보지 않고 치기"지 DP 가 아니다.

**C. 메모이제이션 — 여기선 애매하다**

`(idx, sum)` 으로 캐싱하면 상태가 `20 × 2001` 이라 DP 와 같아진다. 다만 `sum` 이 음수까지 가므로
오프셋을 줘야 하고, 그럴 바엔 B 가 짧다.

### 놓친 엣지 케이스

**제약 내에서 코드가 틀리는 케이스는 없다.** 실제로 돌려 확인한 것:

| 케이스 | 입력 | 기대 | 결과 |
|---|---|---|---|
| 예제 1 | `[1,1,1,1,1]`, 3 | 5 | ✅ |
| 예제 2 | `[4,1,2,1]`, 4 | 2 | ✅ |
| **target > 전체합** | `[1,1]`, 1000 | 0 | ✅ 도달 불가라 자연히 0 |
| **패리티 불일치** | `[1,1,1]`, 2 (합 3, 홀짝 다름) | 0 | ✅ 어떤 조합으로도 못 만듦 |
| **최대 크기** | 1이 20개, target=0 | 184,756 | ✅ 4.9ms |
| 무작위 300건 | N ∈ [2,13] | DP 와 일치 | ✅ 불일치 0 |

- **오버플로우 없음.** 합 ≤ 1,000, `cur` 최솟값 -1,000 이라 `int` 에 한참 못 미친다.
- `1 << nums.length` 는 N ≤ 20 이라 안전하다. 다만 **N 이 31을 넘으면 `1 << N` 이 오버플로우**해
  종료 조건이 조용히 깨진다 — 대안 A 로 가면 이 위험 자체가 사라진다.
- `numbers` 길이 하한이 2라 **빈 배열·원소 1개는 들어오지 않는다.**

### 잘한 점

전체 합에서 시작해 `-2 * num` 으로 부호를 뒤집는 발상이 좋다. `+`/`-` 를 따로 누적하는 것보다 식이 하나 준다.
