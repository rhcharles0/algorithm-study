## 문제 요약

`n × m` 격자에서 좌측 상단에서 우측 하단까지 이동할 때 지나야 하는 칸 수의 최솟값을 구한다. `1`은 이동 가능, `0`은 벽이며 상하좌우로 한 칸씩 움직인다. `1 ≤ n, m ≤ 100`이고 `(n, m) = (1, 1)`은 주어지지 않으며, 도달할 수 없으면 `-1`을 반환한다.

## 풀이 접근

Java 풀이는 이동 가능한 시작점 `(0, 0)`을 큐에 넣고 [BFS](../../../concepts/algorithm/dfs-bfs.md)를 수행한다. 상하좌우 이웃 중 격자 안에 있고 길이며 아직 방문하지 않은 칸을 큐에 넣으면서, 시작 칸을 1로 두고 `visited`에 지나온 칸 수를 기록한다. 탐색이 끝난 뒤 도착 칸의 값이 0이면 `-1`, 아니면 그 값을 반환한다.

## 복잡도

`N = maps.length`, `M = maps[0].length`.

| 언어 | 시간 복잡도 | 공간 복잡도 |
|---|---|---|
| Java | O(N·M): 각 칸은 최대 한 번 큐에 들어가고, 칸마다 4방향을 확인한다. 제한 `N, M ≤ 100`에서 충분하다. | O(N·M): 거리 배열과 큐가 최악에 모든 칸을 담는다. |
| C++ | 풀이 미완성 | - |

## 피드백

### 현재 풀이의 문제점
- BFS와 방문 시 거리 기록은 적절하다. 거리 배열을 방문 표시로 겸해 별도 `visited` 배열을 만들지 않은 점도 간결하다.
- Java의 `N`, `M`은 코테 코드의 읽기 쉬운 변수명 규칙과 맞지 않는다. `rows`, `cols`처럼 의미를 드러내면 된다.
- Java의 이동 방향 배열은 메서드 호출 때마다 새로 만들어진다. 단일 호출에서는 영향이 작아 성능 문제는 아니다.
- Java `Main.java`는 `int[]` 템플릿 케이스라 실제 `int[][] maps` 풀이를 검증하지 못한다.
- C++ 제출본은 항상 `0`을 반환하는 템플릿이고 `main.cpp`의 선언·검증 케이스도 이 문제의 함수 시그니처와 맞지 않는다. 현재 C++ 파일은 이 문제의 풀이·검증본이 아니다.

### 다른 대안
- 현재 Java BFS가 적절하다. `visited` 대신 `maps`에 거리를 덮어쓸 수도 있지만, 입력을 변경하면서 얻는 이점은 없다.

### 놓친 엣지 케이스
- 시작 칸이 벽이면 큐가 비어 결과는 `-1`이다. 도착 칸이 벽이거나 도달 불가능한 경우도 거리값이 0으로 남아 `-1`을 반환한다. 문제 제약의 격자 크기에서는 시작/도착이 같은 칸인 경우는 없다.
